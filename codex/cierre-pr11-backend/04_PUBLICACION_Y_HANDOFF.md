# 04 — Publicación, CI y handoff final

## C5 — Push autorizado y controlado

1. Confirmar que las modificaciones pertenecen al alcance, revisar staged diff y escanear archivos propios por secretos/datos personales (sin imprimir valores sensibles). Versionar arnés, matrices, tests, correcciones y evidencia sanitizada relevante. No versionar .env, dumps, logs masivos, node_modules ni artefactos binarios innecesarios.
2. Ejecutar regresión final en árbol limpio. Atribuir cada ejecución a su SHA de código. Si se añade un commit de evidencias, verificar que solo modifica el paquete documental, no runtime, tests, contrato ni CI; registrar ambos SHAs y diff. Si cambia algo ejecutable, repetir validación.
3. `git fetch origin` y verificar que `origin/feat/sprint-campana-prospector` es ancestro de HEAD mediante `git merge-base --is-ancestor origin/feat/sprint-campana-prospector HEAD`. Si no lo es, no publicar; registrar divergencia. Verificar PR #11 abierto, head/base correctos y ausencia de cambios a otras ramas. No forzar ni ejecutar push masivo.
4. `git push origin HEAD:refs/heads/feat/sprint-campana-prospector` (push ordinario expresamente autorizado). Confirmar SHA con `git ls-remote origin refs/heads/feat/sprint-campana-prospector` y `gh pr view 11 --json headRefOid,baseRefName,state,url` si disponible. No autorizar merge, auto-merge, cambio de estado ni edición del PR.
5. Consultar `gh pr checks 11` y `gh run list --commit <SHA-publicado>`; comprobar que los jobs `quality`, `postgres-integration` y `docker-build` corresponden al SHA del candidato o al merge ref verificable del mismo PR y base. Registrar run ID, URL, evento, head SHA, base si aplica, conclusión por job. No confundir runs antiguos o push de otra rama. Si hay fallo atribuible al candidato, corregir dentro de alcance, repetir gates afectados y push normal; máximo dos ciclos correctivos de CI antes de escalar con log. Si checks pendientes, no hay gh o acceso, dejar PENDING_REMOTE_CI; no cambiar workflows para obtener un verde artificial. No prometer monitoreo fuera de la sesión.
6. Evitar el ciclo infinito de commits de evidencia CI: el recibo del CI posterior al último push se conserva localmente en `evidencias/RECIBO_CI_FINAL.md` (sin commit posterior exclusivamente para registrar ese resultado) y se incluye en el mensaje final con links; el handoff versionado debe indicar que la confirmación remota final se registra aparte. Si hay un commit posterior de producto, repetir verificación y actualizar handoff.

Si hay hallazgos bloqueantes, no publicar una corrección insegura ni una ruptura de contrato; se permite publicar solo auditoría, evidencia o correcciones seguras e independientes, indicando BLOCKED. Si no se puede publicar por credenciales, divergencia u otro motivo, conservar commits y comandos de recuperación manual. No tocar dev/main.

## Reconciliación de ramas (plan, no ejecución sobre ramas compartidas)

PR #10 ya integrado a main con merge commit. Dev no contiene ese commit; el PR #11 inicialmente incluye 44 commits desde dev aunque solo 36 son exclusivos de CP. Inspeccionar graph, merge-base y diff actual tras fetch. Ensayar localmente en un worktree aislado y temporal, sin push ni mover ramas compartidas, la secuencia propuesta: sincronizar dev con main preservando historial (merge normal), luego integrar PR #11 a dev (merge normal), verificar que main es ancestro del dev resultante y que diff neto main..dev corresponde al alcance CP. Puede usarse `git merge-tree` si disponible, y/o commits de merge de ensayo en worktree detached, jamás en rama fuente publicada. No incorporar los merges de ensayo al head del PR. Si hay conflictos, registrar archivos, causas y propuesta; no resolver en dev/main. Comparar árbol de candidato y árbol simulado, volver a probar si hay delta material. No ejecutar sincronización remota, integración ni promoción hasta autorización explícita posterior. Alternativamente, si owner elige integrar PR antes de sincronizar dev, documentar cómo conservar la ascendencia de main antes de promover. No abrir PR adicional.

## C6 — Criterio final

- READY_FOR_OWNER_REVIEW: C0–C5 completos; no P0/P1 abiertos ni defectos que incumplan SPEC/INV o rompan contrato; pruebas locales, migraciones, aislamiento, concurrencia, paridad, integridad y CI remoto del SHA final acreditados; pendientes no bloqueantes explícitos. G6 no está aprobado.
- PENDING_REMOTE_CI: todo lo local cumple, push confirmado, falta concluir/verificar CI remoto exacto. No recomendar merge hasta comprobarlo.
- BLOCKED: fallo obligatorio, falta evidencia crítica, riesgo no resuelto, cambio protegido sin GO, divergencia o push no confirmado. Identificar el siguiente paso y quién lo decide.

El owner puede aceptar riesgos residuales o solicitar cambios; el agente no acepta riesgos de negocio por él. T32, producción, correos reales, deploy, Supabase y promoción a main son NOT_RUN/FUERA_DE_ALCANCE. Los hallazgos de otras ramas/repos quedan registrados como observación, no se ejecutan.

## Entregables mínimos

`evidencias/` debe contener GATES.md, MATRIZ_COMMITS.csv, HALLAZGOS.md, MATRIZ_QA.csv, DIARIO.md, BASELINE.md, MIGRACION.md, CONTRATO_Y_HANDOFF.md, RENDIMIENTO.md, DEPENDENCIAS.md, PLAN_INTEGRACION.md y HANDOFF_FINAL.md. Adjuntar registros sanitizados y pruebas reproducibles (rutas, comandos, fixtures); usar plantillas como mínimos, ampliar cuando sea útil. Registrar hashes de artefactos cuando corresponda. Entregar al final enlace PR, rama, SHA inicial/final, commits añadidos, estado Git, resultados unit/HTTP/PG, migraciones/contrato, riesgos, CI con links y veredicto. Distinguir claramente evidencia histórica de ejecución propia y evidencia local de remota. No afirmar merge realizado. El handoff final debe permitir revisión humana sin rehacer la investigación.
